# 프론트엔드 구현 계획

## 기준 시안

- `sample/App.tsx`: 현재 주간 일정 화면의 정적 마크업과 예시 데이터
- `sample/styles.css`: 현재 시안의 레이아웃과 시각 스타일
- `sample/App.test.tsx`: 시안이 제공해야 하는 핵심 화면 요소의 기준 테스트
- `doc/frontend/주간 스케줄 시안.png`: 최초 디자인 참고 이미지

`sample`은 디자인 비교 기준으로만 사용한다. 실제 기능 코드는 `src` 아래에 구현하며, 기능 구현이 끝날 때까지 시안 파일을 직접 수정하지 않는다.

## 구현 원칙

1. 화면의 시각적 결과는 `sample`을 기준으로 비교한다.
2. 화면 데이터, 사용자 입력, 상태 전이와 검증은 실제 코드에서 분리한다.
3. 서버 API가 확정되기 전에는 타입이 명확한 프론트엔드 fixture와 repository 인터페이스를 사용한다.
4. 비밀번호 등 민감정보를 저장하거나 로그에 출력하지 않는다.
5. 각 단계에서 테스트, lint, build를 통과한 뒤 다음 단계로 진행한다.

## 단계별 진행

### 0. 기준선 보존

- 현재 정적 화면을 `sample`에 보관한다.
- 실제 애플리케이션 진입점에서 시안을 임시로 렌더링한다.
- 시안 테스트와 빌드가 통과하는지 확인한다.

비교 기준: 이동 전후의 화면이 동일해야 한다.

### 1. 도메인 모델 정의

- 팀원, 주간 범위, 30분 시간 슬롯, 개인 가능 시간, 집계 결과와 추천 시간 타입을 정의한다.
- 날짜와 시간 계산 규칙을 순수 함수로 분리한다.
- `00:00`부터 `23:30`까지 48개 슬롯 생성과 주간 경계 계산을 테스트한다.

비교 기준: 화면의 날짜, 팀원 상태와 시간표 셀을 동일한 형태로 표현할 수 있어야 한다.

### 2. 화면 컴포넌트 분리

- 주간 헤더
- 팀원 목록
- 본인 확인 폼
- 주간 가용 시간표
- 범례
- 추천 시간 목록

각 컴포넌트는 데이터를 props로 받고, 예시 데이터를 내부에 직접 선언하지 않는다.

비교 기준: `sample`과 실제 화면의 섹션 위치, 크기, 색상과 반응형 배치가 일치해야 한다.

### 3. 로컬 상태와 입력 구현

- 이름 선택과 비밀번호 입력을 실제 form control로 교체한다.
- 로딩, 입력 오류, 인증 실패와 빈 상태를 표현한다.
- 키보드 조작, label 연결, focus 표시와 오류 안내를 적용한다.

비교 기준: 기본 상태는 시안과 같고, 상호작용 상태가 디자인 체계를 해치지 않아야 한다.

### 4. 일정 선택 기능 구현

- 시간표에서 개인 가능 시간을 선택하거나 해제할 수 있게 한다.
- 클릭 및 드래그 선택, 모바일 터치 조작과 키보드 선택 방식을 정한다.
- 미저장 변경, 저장 중, 저장 완료와 저장 실패 상태를 표시한다.

비교 기준: 집계용 시간표와 개인 편집 시간표가 시각적으로 혼동되지 않아야 한다.

### 5. 집계와 추천 규칙 구현

- 팀원별 가능 시간을 슬롯별 인원수로 집계한다.
- 전원 가능 및 기준 인원 이상인 연속 슬롯을 추천 구간으로 묶는다.
- 동률 정렬, 자정을 넘는 구간과 데이터가 없는 경우를 테스트한다.

비교 기준: fixture 입력으로 `sample`에 표시된 히트맵과 추천 결과를 재현해야 한다.

### 6. 데이터 접근 계층 연결

- UI가 직접 네트워크 요청을 만들지 않도록 repository 또는 client 계층을 둔다.
- 조회, 인증, 일정 저장과 갱신 계약을 타입으로 정의한다.
- 요청 취소, 중복 제출 방지, 오류 변환과 재시도 정책을 적용한다.

비교 기준: fixture와 실제 데이터 소스를 교체해도 컴포넌트 마크업이 바뀌지 않아야 한다.

### 7. 품질 검증

- 주요 사용자 흐름에 대한 컴포넌트 및 통합 테스트를 작성한다.
- 데스크톱, 태블릿과 모바일 레이아웃을 시안과 비교한다.
- 색상 대비, 스크린 리더 표 구조, 키보드 탐색과 focus 순서를 확인한다.
- lint, test와 production build를 최종 실행한다.

비교 기준: 기능 추가 후에도 기준 시안의 정보 우선순위와 레이아웃이 유지되어야 한다.

## 권장 실제 코드 구조

```text
src/
├─ app/
├─ components/
├─ features/schedule/
│  ├─ components/
│  ├─ model/
│  ├─ services/
│  └─ test/
├─ shared/
│  ├─ api/
│  ├─ date/
│  └─ ui/
├─ App.tsx
├─ main.tsx
└─ styles.css
```

폴더는 실제 책임이 생기는 단계에서 추가한다. 빈 폴더나 사용되지 않는 추상화는 미리 만들지 않는다.
